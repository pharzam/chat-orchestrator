# Glossary

Terms, abbreviations, and short definitions for this project. This is the shared
vocabulary the rest of the docs assume. It is the target of the
[Glossary](engineering-discipline.md#glossary) rule, which has two parts. First: any
change that adds a term, renames one, or changes a meaning updates this file in the
same change. Second — **No undefined abbreviation**: every abbreviation used in any
conversation, context, prompt, reply, or response must have an entry here, and any
LLM or operator who uses one that is missing adds it in the same turn. General-English
abbreviations (`e.g.`, `i.e.`, `etc.`) are exempt unless they carry a
project-specific meaning.

## The format — three columns, plus two rules

Each entry is a row in a table:

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| *term* | *abbreviation, or a dash* | *one or two sentences: what it is, and why it matters here* | *a concrete instance that makes it real* |

Two rules keep the glossary earning its place:

1. **Collision to watch for.** When a term means something different outside this
   project — in a common library, a neighbouring team, or the wider field — say so
   in the Description, in the form "Collision to watch for: …". A word that quietly
   means two things is worse than an unknown word.
2. **Quick-reference table.** Keep the whole glossary skimmable. If it grows past
   what a reader can scan, add a short quick-reference table at the top with just
   Term and one-line meaning, and keep the full entries below.

## Discipline vocabulary — the abbreviations these discipline docs use

These are defined here because the discipline documents of this repository use them. Keep this
section as it is; the domain terms are in the sections below.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Large Language Model | `LLM` | A machine-learning model that generates and transforms natural-language text. In these documents it is one of the two operator classes the rules bind, alongside the human operator. | An AI assistant that edits these docs must add any abbreviation it uses to this glossary in the same turn. |
| Architecture Decision Record | `ADR` | A short, numbered document that records one architecturally significant decision and its context. Stored under [`adr/`](adr/). | [`adr/0001-record-architecture-decisions.md`](adr/0001-record-architecture-decisions.md) records the decision to use ADRs. |
| Archived decision record | `D-NNNN` | An [ADR](adr/) that shaped **the baseline itself** rather than a project built with it, kept as closed history under `docs/decisions/` — a directory that the setup removes from a project. It carries a **prefixed, zero-based** identifier in its own namespace, so it shares no number with the living `docs/adr/` sequence and is cited by that `D-NNNN` identifier, not by path. Collision to watch for: a bare `ADR-NNNN` always means the *living* sequence, never the archive. | `D-0003` names the archived frozen-head record — filed as `0008` before the archive was renumbered into its own namespace. |
| Continuous Integration | `CI` | The automated pipeline that builds the project and runs its checks on each change. Collision to watch for: in statistics and machine-learning writing, "CI" usually means *Confidence Interval* — state which you mean. | The cheap validation checks in [`guardrails.md`](guardrails.md) are the ones worth wiring into CI so they run on every change. |
| Massachusetts Institute of Technology License | `MIT` | A permissive open-source software license with short notice and warranty-disclaimer requirements. Collision to watch for: MIT also names the institute that created the license. | A project can reuse an MIT-licensed library when it preserves the required copyright and license notice. |
| Berkeley Software Distribution licenses | `BSD` | A family of permissive open-source software licenses with variants that differ in their notice clauses. Collision to watch for: BSD can also name the related Unix operating-system family. | Before adoption, the team checks which BSD variant applies and preserves its notices. |
| GNU's Not Unix | `GNU` | The recursive name of the free-software project whose licenses include GPL and AGPL. | A dependency can state that it uses a GNU license. |
| GNU General Public License | `GPL` | A copyleft open-source software license that can require distributed derivative work to use the same license. | The team accepts GPL obligations before it distributes a product that includes GPL-covered code. |
| GNU Affero General Public License | `AGPL` | A copyleft open-source software license that extends source-sharing obligations to modified software used over a network. | The team reviews AGPL obligations before it operates a modified AGPL service for users. |
| Application Programming Interface | `API` | A defined interface through which software components or services exchange requests, data, or operations. Collision to watch for: an API can be local code, not only a network service. | A stable API lets a client update without depending on a component's internal code. |
| Facts Document | `—` | A record under [`facts/`](facts/) that stores one customer's requirements or statements as-is, word for word, as immutable evidence. Carries a stable `F-NNNN` ID that derived requirements cite. Collision to watch for: not a data-warehouse "fact table" — this is a source document, not a database row. | `F-0001#2` cites the second fact of the record `F-0001`, the answer to the name of this repository; a requirement written from a fact names that ID. |
| Simplified Technical English | `STE` | A controlled subset of English — the ASD-STE100 standard — with a limited vocabulary and short, active sentences, used for unambiguous technical writing. In these documents it is the language of the derived requirements written from [facts documents](facts/). Collision to watch for: not the same as a [plain-language summary](engineering-discipline.md#plain-language-summaries) — STE is a formal standard, a plain-language summary is just jargon-free prose. | The requirements derived from `F-0007` are written in STE: short, active sentences drawn from the approved word list. |
| Product Requirements Document | `PRD` | Layer 2 of the two-layer facts rule: a versioned document under [`prd/`](prd/) whose every requirement cites the `F-NNNN` fact it derives from. Collision to watch for: not a `PR` (pull request) — a PRD is a requirements document, a PR is a code change. | A `PRD-NNNN` collects a product's requirements; each `REQ`/`NFR` in it names the fact it came from. |
| Requirement ID | `REQ` / `NFR` | The stable ID of one functional (`REQ-NNN`) or non-functional (`NFR-NNN`) requirement in a [PRD](prd/); assigned once, never reused or renumbered. | `REQ-001` states one capability; `NFR-001` states one quality attribute such as a latency bound. |
| MoSCoW | `—` | A prioritisation scheme — Must, Should, Could, Won't — carried in a PRD requirement's priority column, so the statement need not repeat "shall". | A Must requirement ships in the first phase; a Won't is explicitly out of scope, with an em-dash phase. |
| Test-Driven Development | `TDD` | Write the failing test first, watch it fail for the right reason, then write the code that makes it pass. The default order for a feature or a fix. | R8 of the [issue workflow](issue-workflow.md) states TDD in strict mode: red, then green. |
| Pull Request | `PR` | The unit of change review and merge: a branch proposed for landing on the default branch. Every change lands via a PR, never a direct push. Collision to watch for: not a `PRD` — see above. | The [`pre-push` hook](../.githooks/pre-push) refuses a direct push to `main`; a PR is how the change lands. |
| Issue-first workflow | `—` | The rule that an open issue precedes any change, and a PR links back to it — defined in [`issue-workflow.md`](issue-workflow.md) as R1–R13. | No commit starts without an open issue; the PR body says `Closes #N`. |
| Model tier | `—` | The class a model belongs to for [work routing](engineering-discipline.md#model-tiers): a **reasoning tier** (frontier/reasoning models) for work that decides or judges, and an **execution tier** (lighter, faster, cheaper models) for tactical execution and coding once the plan is fixed. Routing applies only after Determinism warrants a model at all. Collision to watch for: not a pricing or API "tier" — this is a role in the gate, not a billing plan. | The review rounds run on the reasoning tier; the code that makes a fixed test pass may run on the execution tier. |
| Panel | `—` | A group of *diverse* specialist agents convened for a complex challenge to [generate and compare candidate options](engineering-discipline.md#solution-selection) and their falsifiable arguments. Its output is a compared candidate set with tradeoffs that feeds Solution selection and the R12 plan — never a verdict, and it does not vote or average. Collision to watch for: not a review panel that returns a decision — a panel here generates options; the [review rounds](engineering-discipline.md#reviewing-until-findings-decay) judge them. | A panel of a security, a performance and a domain specialist proposes three approaches to a novel problem; Solution selection picks among them. |
| Objective-scientist standard | `—` | The rule that every reviewer argues as a curious, empirical, hypothesis-driven, humble scientist — never a **preacher** (defending a convention because it is the convention) nor an **inquisitor** (pressing a finding by interrogation, not by its basis). Stated in [Reviewing until findings decay](engineering-discipline.md#reviewing-until-findings-decay); it sharpens what a finding's *basis* must be — an observation, a test, or a cited clause that could be checked and found false — and buys a vocabulary for a dispute, not a mechanized check. Collision to watch for: it judges a reviewer's *reasoning*, where the [independence levels](engineering-discipline.md#who-may-review) judge a reviewer's *setup*. | A finding whose only basis is "this is not how it is done" is a preacher's finding and fails the standard; one that cites R5 and shows the clause is broken meets it. |
| Solution selection | `—` | The reusable comparison standard for every technical selection, including problem resolution, planning, testing, and choices of software or services. The canonical criteria are in [`engineering-discipline.md`](engineering-discipline.md#solution-selection). | Before a team builds a custom test tool, it searches for public tools and compares suitable candidates with the same standard used to select its work plan. |
| Single-goal issue | `—` | One issue scoped to one actionable, demoable goal (R11); larger work becomes a parent issue with child issues. | A task you cannot demo in one step is really several single-goal issues. |
| Goal class | `—` | A set of Definition-of-Done items that share one failure mode, so a single test failing for one means it fails for all — they stand or fall together. Two items are different goal classes when either can fail while the other passes; a DoD of N independent goal classes is N goals under [R11](issue-workflow.md#r11--single-goal-issues), split unless one mechanism and one test cover them all. Collision to watch for: not a programming *class* — this counts independent goals in a plan, not types in code. | #126's pre-flight named six preconditions — credential, scope, worktree-writable, worktree-in-use, base-branch, hooks — each with its own removal test, so six goal classes under one demo, not one. |
| Test freeze | `—` | The state a test reaches once a fresh context confirms it: it is not weakened or deleted to make new code pass (R9). | A frozen test that later fails opens a bug sub-issue, not a test edit. |
| Requirements traceability matrix | `—` | The table at the end of each [PRD](prd/) that links a requirement across fact, guardrail, ADR, task, and test — the line from the customer's words to the test. | The `§12` matrix's ID set must equal the PRD's requirement set; `prd-lint.sh` checks it. |
| Test level | `—` | One rung of the fixed ladder — unit, integration, end-to-end — ordered cheap-first, so a change runs the cheap levels in the commit hook and the expensive ones in CI. Each level is tagged so it can run on its own. Defined in [`tests/test-levels.md`](tests/test-levels.md). | Tagging tests by level lets the hook run only the unit level while CI runs all three. |
| Unit test | `—` | A test of one component in isolation, with its dependencies replaced by stand-ins, so a failure points at that one component. The cheapest [test level](tests/test-levels.md) and the first to run in the hook. | A pure function's unit test names an input and asserts the exact output, with no file, network, or clock involved. |
| Integration test | `—` | A test that two or more components work together across a real interface or workflow — the seams a unit test stubs out. Slower than a unit test, so it runs after the unit level in the cheap-first order. | An integration test drives a handler through a real datastore and asserts the stored row, not a mocked one. |
| End-to-end test | `E2E` | A test of a whole user-facing path through the running system, front to back, as a real user or caller would exercise it. The most expensive automated level, usually run in CI rather than the commit hook. Collision to watch for: not the same as a `UAT` — an E2E test is automated, a UAT is a human sign-off. | An E2E test starts the app and walks one scenario from first input to final visible result. |
| User Acceptance Test | `UAT` | A scenario a human runs, or signs off, to confirm the delivered behaviour is what was asked — written in plain Given/When/Then steps, not code. It layers on the E2E path but is judged by a person. Collision to watch for: not an automated [test level](tests/test-levels.md) — a UAT is the human acceptance step. | A UAT scenario reads "Given a new account, when the user runs setup, then the welcome screen appears," checked by a person. |
| Definition of Done | `DoD` | The fixed checklist a change satisfies before it counts as finished — tests, docs, review, evidence. In the test section each DoD item maps to a test that proves it, tracked by [`tests/dod-checklist.md`](tests/dod-checklist.md). Collision to watch for: broader than "acceptance criteria" — the DoD applies to every task, the criteria are one issue's. | The DoD item "every requirement has a test" is met by finding a traceability row for each `REQ`/`NFR`. |
| Discipline test | `—` | A test of the *process* rather than the product: it lints the repo's own conventions and needs no product toolchain, so a project has tests before any product code exists. | [`adr/adr-lint.sh`](adr/adr-lint.sh) is a discipline test — it fails a commit whose ADRs break the numbering rule. |
| Portable Operating System Interface | `POSIX` | A standard for a portable Unix-like system; here it names the shell-and-utilities subset the baseline's scripts target. The [discipline tests](tests/test-levels.md#discipline-tests) are written to POSIX `sh` (plus `grep`/`awk`/`sed`), so they run with no extra toolchain on any such system — Linux, macOS, or the Alpine image in the [CI templates](ci/). Collision to watch for: here it means that shell-and-utilities standard, not the wider operating-system interfaces the full standard also covers (threads, signals). | [`run-discipline-tests.sh`](tests/run-discipline-tests.sh) and the linters use only POSIX `sh`, so `/bin/sh` runs them with no interpreter to install. |
| Work slice | `—` | One step of an issue's plan under [R12](issue-workflow.md#r12--slice-and-prioritize): a unit of work scoped to a single domain — a test slice, a datastore slice, a docs slice — that passes the [quality gate](engineering-discipline.md#working-a-task-under-the-quality-gate) on its own. Slices are ordered by dependency and TDD, the test slice first. Collision to watch for: the "domain" a slice is scoped to is an area of the *work*; it is not the baseline's "domain-free", which means the baseline names no *product* domain. | A change to product code has a test slice (done first) and an implementation slice, each its own gate-passing step. |
| Command-line interface | `CLI` | A program a person drives by typing a command and reading its text output. One of the three interface kinds named by the rule that a long operation must show progress ([engineering-discipline.md](engineering-discipline.md#progress-indicators-for-long-running-operations)). | A linter that prints `adr-lint: OK` and exits is a CLI program. |
| Text user interface | `TUI` | A full-screen interface drawn with text characters in a terminal, with its own layout and keyboard control. Named beside the CLI and the GUI in the same progress rule. Collision to watch for: not a CLI — a TUI paints and repaints a screen, a CLI prints a stream of lines. | A terminal dashboard that redraws a progress bar in place is a TUI. |
| Graphical user interface | `GUI` | An interface built from windows, pointers, and drawn controls rather than text. The third interface kind the same progress rule names. | A desktop application that shows a progress bar in a window has a GUI. |
| Artificial intelligence | `AI` | The field of software that makes a machine do work which usually needs human judgement. In these documents it names the class of tool an LLM belongs to. Collision to watch for: not a synonym for LLM — an LLM is one kind of AI system. | An audit measured against a book about AI is still verified against the tree. |
| Identifier | `ID` | The short, stable handle that names one record, so a later reader can find it again. Every task, requirement, fact, and finding has one. | A task's ID stays the same after its card moves to `completed.md`. |
| Secure Hash Algorithm | `SHA` | The fixed-length digest that names one exact commit or one exact file version. Pinning a dependency to a SHA makes the reference immutable, where a tag can move. | An action pinned to a tag can change under you; the same action pinned to a SHA cannot. |
| Change Risk Anti-Patterns | `CRAP` | A code-quality metric that combines cyclomatic complexity with test coverage, so complex and untested code scores worst. Named here as one of the numeric code-quality bars that the baseline does not set. | A search for a CRAP threshold in these documents returns nothing, because no code-quality bar of that kind is written down. |
| HyperText Markup Language | `HTML` | The markup language of web pages. It reaches these documents only as the comment form Markdown borrows, which hides a template line from the rendered page. | The example line in `backlog.md` sits inside an HTML comment, so a reader does not see it. |
| Agent entry point | `—` | A file at the repository root that a coding agent loads when it starts work, so the rules are found rather than looked for. This repository has two, `AGENTS.md` and a one-line `CLAUDE.md` import of it, described in [`agents/README.md`](agents/README.md) and decided by [ADR-0004](adr/0004-ship-agent-entry-points.md). Collision to watch for: not one of the inert forge files under [`templates/`](templates/) — those are copied into place to change a forge's behaviour, while an entry point is live at the root and only tells a reader where the rules are. | An agent that opens `AGENTS.md` first finds the eight gate steps, a pointer to the thirteen rules, and the document that is authoritative for each. |
| Instruction precedence | `—` | The order in which instructions win when two apply: a higher-priority platform or operator instruction outranks the repository's own agent entry point, which in turn defers to the governance documents it summarises. A nested instruction file may add a local constraint and may never weaken the [quality gate](engineering-discipline.md#working-a-task-under-the-quality-gate). | Where `AGENTS.md` and `issue-workflow.md` disagree about a rule, the rule document wins and the summary is corrected in the same change. |
| Independent review | `—` | A review whose reviewer cannot see what the author saw. Independence — not whether the reviewer is a person or an agent — is what the discipline requires, at the four levels set out in [Who may review](engineering-discipline.md#who-may-review): context, method, execution, and model. Collision to watch for: not the forge's "approved" button — a rubber-stamped approval has none of the four levels. | A fresh agent session that sees the issue, the diff, and the source documents, but never the author's reasoning, is context-independent. |
| Review lens | `—` | The one question a review round is asked to answer — correctness, guardrails, clean-and-simple, adversarial bug-hunt, semantic agreement, or one reading. A different lens each round is what makes the [rounds](engineering-discipline.md#reviewing-until-findings-decay) decay rather than repeat. | Two agents given the same lens and the same prompt are one reviewer run twice, not two reviewers. |
| Semantic agreement | `—` | That a changed sentence still means what its source means. It is the residual the baseline's deterministic checks explicitly do not cover — they prove coverage and structure, never meaning — so it is closed by a clause-by-clause [review](engineering-discipline.md#reviewing-for-semantic-agreement) recorded on the issue. Collision to watch for: not "the linter passed" — a stub of filler words with the right headings passes every assertion. | A summary that softens a "must" to a "should" keeps full coverage and loses semantic agreement. |
| Decision-driving text | `—` | The text an operator acts on, which must admit [one honest reading, not two](engineering-discipline.md#one-reading-not-two) and be falsifiable ([R13](issue-workflow.md#r13--one-reading-not-two)): the issue statement, the acceptance criteria and Definition of Done, a directive to another operator, a plan step, and a review finding. Collision to watch for: narrower than "documentation" — casual prose, a commit message, or a terminal reply is not decision-driving text, and the one-reading rule does not bind it. | An acceptance criterion a reviewer can read two honest ways is decision-driving text with two readings, so R13 sends it back to be rewritten, not interpreted. |
| Cycle cap | `—` | The maximum number of fix-and-review cycles a task may run after its first frozen head, declared in the plan-review confirmation and defaulting to two. Reaching it with something material still in scope ends the task at `not mergeable, findings recorded`. Collision to watch for: not a **ceiling**, which bounds how large a change may grow, while a cap bounds how many times it may be revised. | A task whose third round still finds a material defect has reached a cap of two and is split rather than fixed again. |
| Issue split | `—` | The successor state of `not mergeable, findings recorded`: one successor issue carrying the branch's work as it stands, on a branch of its own cut from that commit, plus a child issue for each finding still open that the successor does not take. Where the successor takes every open finding, it alone is the split; an unapproved overrun is always among the findings it takes. Collision to watch for: not a parent-and-child decomposition under R11, which happens before work starts; a split happens after a task has stopped. | A branch stopped at its cap is not abandoned — its successor starts from the same commit, with the findings as its Definition of Done. |
| Ceiling | `—` | **A thing this discipline does not have.** An approval is one number, named once, and it is the figure at landing; it reaches that figure and no further. Three review rounds each wrote a way for an approval to reach past its number — left open, bounding the measured outturn, covering findings-driven growth — and a later round falsified each, so the reach does not exist. Collision to watch for: not the **cycle cap**, which bounds how many times a change may be revised, where a ceiling would have bounded how large it may grow. | Growth past the approved figure is absorbed, routed to a child issue where the finding is non-material, or ends at the cap in a split. There is no second approval. |
| Review record | `—` | What one review round writes on the issue so a later reader can check it, under the heading `## Review record — round N`: the commit reviewed, the reviewer, the lens, what it was briefed on, what it was barred from, the independence claimed, the cycle, the raw findings, the fixes, and the verdict — ten fields, fixed by [What a round records](engineering-discipline.md#what-a-round-records). The reviewer writes nine; `Fixes` is the author's, added as a reply under the round it answers, because the fixes land after the round ends. A verdict that does not name what it read is not evidence, and the verdict itself comes from a closed vocabulary. | "LGTM" is not a review record. Neither is "reviewed `c98f807` under the adversarial lens, three findings, all fixed": it names no cycle, no brief and no bar, so a later reader cannot check what the reviewer could see. |
| Resource record | `—` | The model, effort, tokens and elapsed time a task spent, per gate **part** and in total, written as a section (after `## Verdict`) of its [`tasks/<id>.md`](tasks/) file at close-out and required by gate step 8 ([ADR-0007](adr/0007-record-task-resource-use.md), which decides it against the [routing](engineering-discipline.md#model-tiers) it evidences). **Recorded, not budgeted** — it carries no approval number and no cap, and an overrun of tokens or time is not a finding. Collision to watch for: not the **review record**, which is what a review round writes on the *issue*; a resource record is what a task writes in its own *file* about what running it cost. | A row whose expected tier is *reasoning* but whose model is an execution-tier one is a mismatch a reader raises; `not reported` fills a cell the harness cannot, and a human part's model columns read `not applicable`. |
| Heading anchor | `—` | The fragment a link uses to jump to one heading — the part after `#`. A forge derives it from the heading text by a fixed **slug** rule: lowercase, drop punctuation, and replace **each** space with a hyphen. Collision to watch for: the rule does not collapse runs, so `## R5 — Deterministic over LLM-based` yields `r5--deterministic-over-llm-based` with **two** hyphens, because removing the em-dash leaves two spaces. [`link-lint.sh`](links/link-lint.sh) checks these. | A checker that collapses whitespace reports 25 false failures on this repository's own rule anchors. |
| Material | `—` | Of a finding: one that changes an exit code, an assertion, a behaviour on a project's tree, a claim in the tree, or a Definition-of-Done item; wording, style and layout are not. A claim in the tree counts only when a reader could act on it and the change makes it false or leaves it false. Defined in the [review rounds](engineering-discipline.md#reviewing-until-findings-decay), which stop on `nothing material in scope`. Collision to watch for: not the everyday "important" — a finding can matter to a reader and still be wording. | A `must` softened to `should` in a rule is material; a comma moved in the same sentence is not. |
| Frozen head | `—` | The named commit a review round reads. Nothing lands on the branch after it except a fix to a finding of that round, a plain merge of the default branch, which re-freezes the head and consumes no cycle, or the close-out bookkeeping that gate step 8 requires of the landing pull request; the first two produce a frozen head a next round names, the close-out is named by none, and the last round's verdict is on it. A branch carrying such a verdict is never rebased, because a rebase rewrites the SHA the verdict names. Collision to watch for: not version control's `HEAD`, which moves with every commit — a frozen head is one SHA written into the review record, and it stays that SHA after the branch moves on. | Round 2 reviewed `c9af4e4`; its fixes landed as `b569583`, which round 3 named as its frozen head and found nothing material in. |
| Revealed defect | `—` | A defect a review round finds that is pre-existing and off the path the Definition of Done names. It leaves the branch as a new issue, opened by the author with its measurement before the merge — a blocker if it is a silent false green, normal if it fails loudly. Its counterpart is a defect *in the change*, fixed inside the budget. Collision to watch for: "revealed" says where the defect sits, not who found it — a defect the branch itself introduced is in the change however it came to light. | A linter that misreads a spaced path, found while reviewing a change to a different check, opens its own issue instead of entering the branch. |

## 1. Conversations and requests

The words of the problem statement, [`facts/problem-statement-brief.md`](facts/problem-statement-brief.md) (sections 1.2, 3 and 4). `R-XXX-nn` is the ID of a requirement of that file.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Session | `—` | One stored conversation, created empty by `POST /v1/sessions`. It has a server-generated UUID, an owner `(tenant_id, subject)`, a locale, retrieval settings and a conversation version. Collision to watch for: not a login session or an HTTP cookie; the client holds only the session ID, and the state is in the database. | A client that comes back after a restart sends the same session ID and goes on. |
| Turn | `—` | One user message and the conversational response to it. A turn exists only when it is committed. Collision to watch for: not an HTTP request and not an attempt; one turn can follow several attempts. | A turn that ended in `cannot_answer / no_evidence` is still a committed turn. |
| Logical request | `—` | One question that a client sends, named by `(tenant_id, subject, session_id, request_id)`. It commits at most one user and assistant pair (`R-INV-02`). | Sending the same `request_id` again after a timeout means the same logical request. |
| Request ID | `—` | The identifier that the client chooses for one logical request: ASCII letters, digits, hyphen and underscore, at most 128 bytes. | `req-123` |
| Attempt | `—` | One admitted execution of a logical request. A retry of an interrupted attempt is a new attempt, with a new admission sequence. Collision to watch for: not a new logical request; the key does not change. | Attempt 2 of `req-123` starts after attempt 1 stopped with no unresolved paid call. |
| Provider call | `—` | One separately journaled outbound call that can cost money: a Decision Model call, a summary call, a generation call, or a KB call that is billable. | An intent classification by Jev is one provider call. |
| Conversation version | `—` | The integer that goes up by one with each committed turn. A retry compares it with the version that it was bound to (`R-IDEM-07`). Collision to watch for: not the version of the service or of the API. | After 7 committed turns the version is 7; the next committed turn makes it 8. |
| Committed message | `—` | A transcript message that is written, with its sequence number and its sources, in the transaction that commits the turn. It does not change after that. | The user message with sequence 15 and the assistant message with sequence 16. |
| Transcript | `—` | The ordered committed messages of one session. It is the authority; a summary only makes it shorter for a model (`R-STATE-07`). | `GET /v1/sessions/{session_id}/messages` returns it in pages. |
| Outcome | `—` | The result of a committed turn: an `action` (`answer`, `ask_clarification` or `cannot_answer`) and a `reason_code` (`R-API-10`). All three actions are successes and count as a turn. Collision to watch for: not a state of the request. | `cannot_answer / out_of_scope` |
| Idempotency | `—` | The property that the same logical request, sent again, never makes a second turn: it gets the saved result or the stored state back. | A repeated `POST /v1/chat` after `completed` returns the saved answer with `Idempotent-Replayed: true`. |
| Semantic-input fingerprint | `—` | The versioned hash of the exact question, the resolved locale and the retrieval settings of the session. The same key with another fingerprint gets `409 IDEMPOTENCY_CONFLICT`; transport timestamps and renewed token bytes are not in it (`R-IDEM-02`). | The same `request_id` with a changed question text. |

## 2. Request states and recovery

The brief, section 5.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Request state | `—` | The stored state of a logical request: `queued`, `running`, `committing`, `completed`, `retryable`, `uncertain` or `failed_final` (`R-IDEM-09`). | `GET /v1/sessions/{session_id}/requests/{request_id}` returns `state` and `next_action`. |
| Retryable | `—` | The state of a request whose work stopped in a way that leaves no unresolved paid call, so the same key can be admitted again. It must pass the retry-version guard when it runs, not when it is queued (`R-IDEM-06`). | A disconnect during the wait in the queue. |
| Uncertain | `—` | The state of a request with a paid call that may have been sent and whose result cannot be shown. The same key gets `409 OUTCOME_UNCERTAIN`, and the service starts no new attempt by itself. Collision to watch for: not "failed"; it says that the outcome is not known. | A crash after the dispatch marker and before the provider answered. |
| Failed final | `—` | The state after a known failure that cannot be retried. The saved problem is replayed, and the client needs a new request ID. | `502 CITATION_INVALID` |
| Retry-version guard | `—` | The conversation version that a retry must still see when it starts to run: its execution version, or its admission version if it never ran. If the version differs, the answer is `409 STATE_CONFLICT` and no paid call is made (`R-IDEM-06` to `R-IDEM-08`). | Request A1 cannot retry after request A2 has committed a turn. |
| Dispatch intent | `—` | The durable marker that the service writes before each call that can cost money, with a call ID, the stage and the writer epoch. It means "may have been sent". If it cannot be written, the call is not sent (`R-IDEM-12`, `R-IDEM-13`). | A crash between the marker and the send gives a safe, false `uncertain`. |
| Journal | `—` | The durable records of the work of a request: the request journal and the provider-call journal, with saved normalized results. Collision to watch for: a log line is not a journal. | A saved summary result lets a retry go on with no new paid call (`R-IDEM-15`). |
| Reconciliation | `—` | The step that reads the stored evidence to decide the true state of a request after a lost acknowledgement, a crash or a timeout. A committed result wins over a lost connection. | After a lost commit acknowledgement, the service looks for the saved result before any new inference (`R-STATE-06`). |
| Guarantee boundary | `—` | The promise that is made and the one that is not: at most one durable turn for each logical request is required; exactly one provider charge across any network failure is not promised (brief section 5.4). | A possible second charge is recorded in its own ledger (`R-IDEM-18`). |

## 3. Ownership and scheduling

The brief, sections 6 and 7.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Writer | `—` | The one process that may change the database and send calls that can cost money. Collision to watch for: its ownership connection is dedicated; it is not a connection that a pool lends for each operation. | A second process stays not ready. |
| Advisory lock | `—` | A PostgreSQL session lock that the writer takes on a dedicated connection and keeps until that database session ends. It is not a lease with a time limit (`R-WRITER-01`). | Loss of that connection fails readiness (`R-WRITER-06`). |
| Instance epoch | `—` | The number that grows each time a new writer takes over, written in a control row before recovery. Each write and each dispatch marker checks it in its own transaction (`R-WRITER-03`, `R-WRITER-04`). | A late write with the old epoch is refused. |
| Fencing | `—` | The use of the epoch so that an old writer cannot change the database after a new writer starts. It does not undo a call that a provider already accepted. | The successor publishes its epoch with an exclusive update. |
| Active turn | `—` | A turn that holds a global slot, from the loading of its state to the end of its finalization. At most 100 at a time, and one for each session (`R-INV-01`). Waiting requests hold none. | The 101st turn starts only after one of the 100 ends. |
| Admission | `—` | The decision to accept a request: the global, session and principal limits and the estimated start delay are checked, and a durable claim is made. Overload gives `429` with `Retry-After` and stores nothing (`R-IDEM-04`, `R-SCHED-08`). | `QUEUE_FULL` |
| Admission sequence | `—` | The order number that the server gives when it admits a request. The order inside a session follows it, not client clocks (`R-SCHED-02`). | A retry gets a new admission sequence, and so a new place in the queue. |
| Principal | `—` | The identity that the service builds from the token: `{tenant_id, subject, roles, authz_version}`. Quotas and ownership are by principal. | One subject cannot use many sessions to take all 100 slots (`R-SCHED-05`). |
| Tenant | `—` | The customer organization in the `tenant_id` of the token. It is part of the owner and of every logical key. | `tenant_id` has at most 128 bytes. |
| Deadline | `—` | The absolute 180-second limit of one attempt, from the entry of the handler, with a 60-second cap on the queue and 5 seconds kept for finalization (`R-TIME-01`). | A request that waited 60 seconds expires to `retryable`. |

## 4. Knowledge, decisions and generation

The brief, sections 8 to 10.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Knowledge Base | `KB` | The external system that returns evidence for a question. The service has the outbound adapter and the mapping, not a retrieval engine (`R-SCOPE-04`). Collision to watch for: not the database of the service; conversations are in PostgreSQL, and evidence comes from the KB. | Up to 8 evidence items come back for a question (`R-KB-05`). |
| Evidence item | `—` | One normalized passage from the KB: text, document ID, chunk ID and, when the KB gives them, a revision, a title and a reference. | Document `doc-42`, chunk `chunk-3`, revision `rev-7`. |
| Citation | `—` | A marker in a generated answer, such as `[S1]`, that names one evidence item that the call was given. An answer with no valid citation is not committed as `grounded` (`R-LLM-07`). | `sources` holds exactly the cited items, in the order of the first citation (`R-LLM-09`). |
| Decision Model | `—` | The replaceable component that gives typed judgments about a question and its evidence. The service owns its contract and its adapters. | TypeSafe AI Jev is the first adapter. |
| Jev | `—` | The TypeSafe AI model that is the first real Decision Model, called through the pinned `POST /v1/systemone` contract (`R-DEC-01`). | An intent call and an evidence call are two Jev calls. |
| Noul | `—` | The TypeSafe primitive for one atomic yes-or-no question. Its answer has a probability p, and no separate confidence field. A distance that is derived from p carries a label that says so (`R-DEC-08`, `R-DEC-09`). | `needs_clarification` is one such question. |
| Intent | `—` | The class that the Decision Model gives to a question before retrieval: `domain`, `conversation_meta`, `smalltalk` or `out_of_scope` (`R-DEC-03`). Ambiguous intent asks for a clarification (`R-DEC-04`). | A thank-you is `smalltalk`: no KB call (`R-POLICY-02`). |
| Assessment | `—` | One of the three judgments after retrieval: `needs_clarification`, `evidence_sufficient` and `evidence_conflicting`. Each is `yes`, `no` or `uncertain`, and the raw probability is kept apart (`R-DEC-05`, `R-DEC-06`). | In the Jev profile, `evidence_sufficient` is `yes` when p is at least 0.85. |
| Policy table | `—` | The first-match table that turns the assessments into one action (`R-POLICY-01`). Contradictory judgments have one result. | Clarification comes before missing evidence; conflict comes before sufficiency. |
| Policy profile | `—` | The versioned set for one provider and model: thresholds, question text, normalization rules and the order of actions (`R-DEC-07`). A change of one needs the quality run before promotion (`R-QUAL-08`). | The Jev profile with the intent thresholds 0.70 and 0.20 (`R-DEC-04`). |
| Model drift | `—` | A returned model ID that is not an approved one. It gives `503 MODEL_PROFILE_MISMATCH` before any judgment is used (`R-DEC-10`). | A moving alias that now points to a new model. |
| LLM adapter | `—` | The code that maps the generation and summary contract of the application to one provider protocol: Anthropic Messages, or OpenAI-compatible Chat Completions. Both pass one shared conformance suite (`R-LLM-02`). Collision to watch for: compatible does not mean the same caching, structured output, usage fields or price. | A capability that a profile needs and the endpoint lacks fails the configuration (`R-LLM-04`). |
| Provider refusal | `—` | A valid refusal of a model to answer. It is a successful outcome, `cannot_answer / provider_refusal`, not an infrastructure error (`R-LLM-11`). | No second provider is tried. |
| Untrusted data | `—` | Everything that comes from a user, the KB or a summary. It is data, never an instruction to the service or to a model (`R-KB-09`). | A KB passage that says "ignore your rules" changes nothing. |

## 5. Context, cache and cost

The brief, sections 11 to 13.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Context budget | `—` | The limit on the input, the output and the bytes of one call, set for each role by its own profile. `estimated_input + reserved_output + safety_margin` must fit the window (`R-CTX-02`). | A summary call has its own window, not the window of generation. |
| Summary checkpoint | `—` | Derived, bounded (4 KiB) text that stands for the older part of a session, saved with its coverage and its source hash. It does not change the conversation version and it does not replace the transcript (`R-STATE-09`). | `covered_seq` 40 means that the messages up to sequence 40 are in the summary. |
| Covered sequence | `covered_seq` | The sequence number of the last message that a summary covers completely. A cursor can record that a long message is covered in part. It only grows. | A summary pass moves it forward or fails in a stated way (`R-CTX-07`). |
| Catch-up summarization | `—` | The bounded, repeated passes that bring a summary up to date. Each pass makes durable progress or fails in a stated way (`R-CTX-07`, `R-CTX-10`). | `503 CONTEXT_PREPARING` says that progress was made and more is needed. |
| Prompt caching | `—` | The reuse, by a provider, of a stable beginning of a prompt. The service builds prompts with a beginning that is the same byte for byte, and never depends on a hit for correctness (`R-CACHE-02`, `R-CACHE-06`). Collision to watch for: not a cache of answers, which the pilot does not turn on. | A cache read that the provider reports in its usage fields. |
| Cache intent | `—` | The setting `auto`, `prefer_reuse` or `no_explicit_cache`, apart from the hard constraint `require_no_prompt_cache`, which a profile either verifies or fails before it sends private content (`R-CACHE-03`, `R-CACHE-04`). | The default intent is `prefer_reuse`. |
| Usage record | `—` | The durable record of one inference attempt, with each number marked `reported`, `estimated` or `unknown`. Missing usage is never turned into zero (`R-USAGE-02`). | A call whose provider gave no usage fields has `unknown` usage. |
| Price profile | `—` | A dated list of prices that an estimated cost uses. No price is assumed when a profile is missing (`R-USAGE-06`, `R-CONTRACT-03`). | Reported charges and estimates are shown apart. |

The brief, sections 14 to 16.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Problem details | `—` | The error format `application/problem+json` of RFC 9457, with a stable application `code`, `retryable` and the request state (`R-ERR-01`). | `409 OUTCOME_UNCERTAIN` |
| Authorization fingerprint | `—` | The value that a session stores for its trusted owner, roles, retrieval scope and authorization revision. A changed value blocks history, replay and model context with `SESSION_AUTHORIZATION_CHANGED` (`R-SEC-06`, `R-SEC-07`). | A role that was removed from the token. |
| Tombstone | `—` | The atomic mark that a session is deleted, made before its content is purged, so that no admission, summary write or commit can bring it back (`R-DELETE-03`). | An interrupted purge is finished by a repeated `DELETE`. |
| Reserved ID registry | `—` | The protected digests of session IDs that were allocated or deleted, kept apart from content, so that an ID is never reused (`R-DELETE-05`, `R-DELETE-06`). | A new session ID is checked against it. |
| Synthetic mode | `—` | The labelled mode for tests and development, with in-memory storage or no real identity. It does not satisfy durable-persistence acceptance, and it is not used for real personal data (`R-PROFILE-02`, `R-PRIV-05`). | A development run with a local signing key. |

## 7. Delivery gates and acceptance

The brief, sections 18 to 21.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Gate A | `—` | The offline set of deterministic tests: formatting, build, `go vet`, unit, contract, store and end-to-end tests, and the race detector, with a local PostgreSQL (`R-GATE-02`, `R-TEST-05`). A missing prerequisite or a skipped mandatory test is a failure. | `go test -race ./...` |
| Gate B | `—` | The separate live check of the real KB, the pinned Jev profile and at least one real LLM, and of a native-cache claim by a positive cache read that the provider reports (`R-GATE-03`, `R-GATE-04`). | A cache profile with no positive read stays `unverified`. |
| Gate C | `—` | The model-quality run on a frozen labelled set, twice for each release profile, against floors that are fixed before the run (`R-QUAL-04`, `R-QUAL-05`, `R-GATE-05`). | At least 80% of the answerable domain cases answered. |
| Acceptance family | `—` | One of the named groups `A01` to `A38` of required proof, each with named subtests (`R-TEST-06`). | `A04` reaches 100 active turns and never a 101st. |
| Traceability file | `—` | `docs/tests/traceability.json`: one entry for each normative requirement ID, with its acceptance IDs, test names, evidence and status. CI refuses duplicates, unknown IDs and a skipped test that is shown as passed (`R-TRACE-01`, `R-TRACE-02`). | The status is `planned`, `passed`, `failed`, `blocked` or `unverified`. |
| Contract closure | `—` | The step that fixes the interface inputs before the affected work, and Gate A, are called complete: the wire contract of the KB, the identity profile, the storage pin, the LLM protocols and the budgets (`R-CONTRACT-01`). An invented endpoint or price is never a substitute. | The wire contract of the KB is not yet supplied. |
| Repository bootstrap | `—` | The setup of this repository and the external run of its gate. It is reported apart from the completeness of the product and from the live and quality acceptance (`R-GATE-06`). Collision to watch for: a green scaffold proves no chat requirement. | `layup setup verify` passes, and no service code exists yet. |
